# B7-03 耗时与取证路径调查

## 历史事实与证据边界

审核人报告：相同代码 e9dc3a2 的 push run 38747671974 在 B7-03 的助手请求发生 httpx.ReadTimeout（15 秒），PR run 38747683827 则 37/37 GREEN。已下载前者 report-B7 原始产物，确认 failed_check 为 exception，错误末行为 `httpx.ReadTimeout: timed out`。整个用例耗时约 31.70 秒，其中还包含清空、安装、启动、导入；**不能把这个总耗时当作回答耗时**。

原产物未记录上下文/搜索/模型/历史写入的分段时间，不能事后断言那次超时就是联网卡住、模型重试或超大上下文。源码追踪又发现：空模板库 project 数为 0，该题未指定项目，原来的 `_refusal_for` 返回 PROJECT_NOT_FOUND；local_agy_facade 随后把这句周报问题交给 `_general_chat_reply`。该分支至多调用模型一次，没有软件搜索、没有证据修复重试，发送的只是一般对话指令及有限历史。**按这条可复现路径，搜索、证据重试和超大项目上下文均不是合理的直接归因；历史那次请求到底在哪一步停顿，仍未确认。**

此前的 mock 在缺少上下文时也默认使用 sample_doc.docx 及固定事实，所以旧题“引用文件名”通过不能独立证明产品正确检索了刚导入的资料。C-03 删除了这种回答兜底，不改题目或预期：mock 只从请求携带的上下文通用摘句并附合法 evidence id；建议类段落带“建议”标注。没有读取 pending/exam 或按题目/题号分支。

## 已确认并修复的产品问题

1. 全局上下文不读取已解析但未形成正式业务资产的文档。现在将这些原文以明确标注的非正式资料证据加入上下文；它们不是已核准事实。文档族中过期的来源及其旧派生记录不进入当前问答。
2. 有文档证据但没有项目的资料问题错误进入一般对话。现在保留全局资料取证路径；项目不确定仍不会自动归属、改项目或改正式结论。
3. 搜索策略存在另一个独立的慢路径：零证据可启动搜索，四个后端原来分别拥有完整等待预算，DuckDuckGo 内部还有两个端点。现在已有工作台证据或内部文档问题不因“零证据”联网；明确联网请求仍可搜索，后端/端点回退共享剩余预算。这一代码风险真实存在，**不是已证明的历史 B7-03 超时根因**。网络库的单次连接/读取超时并非严格的整个 HTTP 墙钟期限，不宣称能够强杀所有卡住的系统调用。
4. B7-03 原来固定等导入 3 秒，改为等待扫描及来源处理实际完成，仍使用已有扫描等待上限。回答请求原有 **15 秒上限未变**。

## 观测

- `tests/run_e2e_tests.py::timed_answer` 在 finally 中记录每一次 B7-01、02、03 和版本问答的 HTTP 墙钟耗时，失败也记录；不打印回答正文或 Key。
- `backend/pm/answer_timing.py`、助手上下文构建和 Provider 记录 numeric timings：total_seconds、context_seconds、context_bytes、evidence_count、model_calls、model_seconds、prompt_bytes、search_seconds。返回给测试，在日志中保存；不记录提示词或用户原文。
- 本地单元测试验证内部问题不联网、回退共享预算、计时不包含正文，以及通用摘句不编造文件名。没有连接搜索服务器做复现。
